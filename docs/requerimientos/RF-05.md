# RF-05: Gestión del Catálogo de Servicios (CRUD)

> **Semana:** 2 · **Ubicación en el código:** `plugins/clinica`
>
> Lee también la sección **Adaptación a Firebase** al final: prevalece sobre el texto original cuando hay conflicto.

## Módulo

Módulo: Clínica Veterinaria

## Actor(es)

Usuario Clínica; Backend/API

## Precondiciones

1. La clínica tiene el perfil de atención configurado (RF-04).

## Disparador (Trigger)

La clínica accede a la sección "Servicios" y pulsa "Agregar Servicio", o selecciona un servicio existente para editar/eliminar.

## Flujo Principal (Paso a Paso)

1. [Usuario] Pulsa el botón flotante "+ Nuevo Servicio".
2. [UI] Abre un formulario modal con los campos: Nombre del servicio (texto), Categoría (dropdown: Vacunación, Peluquería, Baño, Cirugía, Consulta general, Otro), Descripción (texto largo, opcional), Precio (numérico, moneda local), Duración estimada en minutos (numérico).
3. [Validación Frontend] Nombre: obligatorio, 3-60 caracteres. Precio: obligatorio, mayor a 0, máximo 2 decimales. Duración: obligatorio, entero entre 5 y 480 minutos.
4. [Usuario] Completa los campos y pulsa "Guardar".
5. [Frontend] Envía POST /clinics/{clinicId}/services con el payload validado.
6. [Backend/API] Verifica pertenencia del clinicId al usuario, crea el documento en la subcolección services con estado activo: true.
7. [Base de Datos] Emite evento realtime que actualiza la lista de servicios visible en la app del dueño de mascota (para esa clínica) sin necesidad de recargar.
8. [UI] Cierra el modal, inserta la nueva tarjeta de servicio en la lista con animación, y muestra confirmación.
9. [Usuario] Para editar: pulsa sobre una tarjeta de servicio existente, modifica campos en el mismo modal (precargado) y pulsa "Actualizar".
10. [Backend/API] Ejecuta PATCH /clinics/{clinicId}/services/{serviceId}; si el servicio tiene turnos futuros ya agendados, actualiza el precio solo para nuevas reservas (no afecta appointments existentes).
11. [Usuario] Para eliminar: desliza la tarjeta o pulsa el ícono de papelera; el sistema solicita confirmación.
12. [Backend/API] Ejecuta un borrado lógico (soft delete): activo:false, en lugar de eliminar el documento, para preservar la integridad histórica de citas ya realizadas con ese servicio.

## Flujos Alternativos y Excepciones

- Servicio con turnos activos al eliminar: Si existen citas en estado 'pendiente' o 'confirmada' asociadas al servicio, el sistema muestra advertencia: "Este servicio tiene N citas activas. Se ocultará del catálogo pero las citas existentes no se verán afectadas", requiriendo confirmación explícita.
- Datos inválidos: Los campos con error se resaltan en rojo con mensaje específico bajo cada uno (ej. "El precio debe ser mayor a 0"); el formulario no se envía.
- Fallo de red al guardar: El frontend conserva los datos ingresados en el formulario (no se pierden) y muestra opción de reintentar.

## Postcondiciones

- El catálogo de servicios queda actualizado en tiempo real para todos los clientes que consulten esa clínica.

## ⚠️ Adaptación a Firebase (prevalece sobre el texto original)

- CRUD directo a `clinics/{clinicId}/services`. Soft delete (`activo:false`). Las reglas validan tipos y rangos (nombre 3-60, precio > 0, duración 5-480).
- Las citas guardan una copia del precio (`precioAcordado`), así un cambio de precio no afecta citas existentes.
