# RF-02: Inicio de Sesión (Login con Google)

> **Semana:** 1 · **Ubicación en el código:** `core/auth`
>
> Lee también la sección **Adaptación a Firebase** al final: prevalece sobre el texto original cuando hay conflicto.

## Módulo

Módulo Transversal: Autenticación y Acceso

## Actor(es)

Usuario registrado; Proveedor de Identidad (Google); Backend/API

## Precondiciones

1. El usuario cuenta con un registro previo válido en la colección users.
2. El dispositivo tiene conexión a internet.

## Disparador (Trigger)

El usuario pulsa el botón "Iniciar sesión con Google" en la pantalla de bienvenida.

## Flujo Principal (Paso a Paso)

1. [Usuario] Pulsa el botón "Iniciar sesión con Google".
2. [Frontend] Invoca el SDK de Google Sign-In; si existe una sesión de Google activa en el dispositivo, el selector de cuentas se omite (silent sign-in).
3. [Frontend] Obtiene el idToken y lo envía a POST /auth/login.
4. [Backend/API] Verifica el idToken contra Google y busca el UID en la colección users.
5. [Backend/API] Genera un access token JWT (expiración 60 min) y un refresh token (expiración 30 días), y los retorna al frontend.
6. [Frontend] Almacena el access token en memoria (Provider/Riverpod state) y el refresh token en almacenamiento seguro (flutter_secure_storage / httpOnly cookie en web).
7. [Base de Datos] Actualiza el campo lastLoginAt del documento del usuario mediante escritura parcial (update).
8. [UI] Redirige al Home correspondiente según el campo role: Dashboard de Clínica o Home de Dueño de Mascota.
9. [UI] Establece los listeners realtime necesarios para el rol (citas, notificaciones, chats activos) inmediatamente después del login exitoso.

## Flujos Alternativos y Excepciones

- Usuario no registrado: Si el UID no existe en users, el backend retorna error 404; el frontend redirige automáticamente al flujo de Registro (RF-01) prellenando el correo detectado.
- Cuenta suspendida: Si el documento del usuario tiene estado: 'suspendido', el backend rechaza el login con error 403 y el frontend muestra "Tu cuenta ha sido suspendida. Contacta a soporte", sin generar tokens.
- Token expirado durante uso de la app: Si una petición retorna 401 por token expirado, el frontend intenta renovar automáticamente usando el refresh token contra /auth/refresh; si el refresh también falla, se fuerza el cierre de sesión (RF-03) y redirección a la pantalla de bienvenida.

## Postcondiciones

- El usuario tiene una sesión activa con tokens válidos almacenados de forma segura.
- Los listeners de datos en tiempo real correspondientes a su rol están activos.

## ⚠️ Adaptación a Firebase (prevalece sobre el texto original)

- **No hay JWT propio ni refresh token propio.** Firebase Auth emite el ID token (1 h) y lo renueva solo. Se elimina `/auth/login` y `/auth/refresh`.
- Tras el login: si no existe `users/{uid}` → ir a selección de rol (RF-01). Si `estado == 'suspendido'` → cerrar sesión y mostrar el mensaje. Además, la cuenta se deshabilita en Firebase Auth (Admin SDK) para bloquearla del todo.
- `lastLoginAt` se actualiza desde el cliente (permitido por las reglas solo sobre ese campo).
- El enrutamiento por rol lo resuelve `go_router` con un `redirect` que lee el estado de sesión (Riverpod).
